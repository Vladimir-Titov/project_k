# Project Context: Browser Turn-Based RPG

## 1. Общая концепция

Проект представляет собой браузерную многопользовательскую RPG, вдохновлённую играми:

* `https://w2.dwar.ru/`
* `https://3kingdoms.ru/`

Заимствуется не конкретный контент или сеттинг, а общий формат:

* постоянный игровой мир;
* персонажи игроков;
* связанные между собой локации;
* перемещение между локациями;
* общие монстры в локациях;
* режим охоты;
* пошаговые бои;
* развитие персонажа;
* экипировка и ресурсы;
* несколько игровых валют;
* позднее — торговля, групповые бои и социальные механики.

Сеттинг и сюжет пока не определены. На первом этапе приоритет отдан техническому прототипу, боевой системе и развитию персонажа.

## 2. Масштаб и формат разработки

Проект разрабатывает один человек с использованием AI-агентов.

На старте:

* платформа — браузер;
* интерфейс преимущественно статичный;
* бой может использовать простые 2D-анимации;
* полноценная мобильная версия не требуется;
* интерфейс должен быть минимальным, без необходимости сразу создавать production-ready дизайн;
* первые пользователи — разработчик и несколько друзей;
* возможен закрытый тест на 50–100 человек.

Архитектура не должна преждевременно оптимизироваться под тысячи игроков, но основные модели должны допускать дальнейшее масштабирование.

## 3. Основной архитектурный подход

Используется:

> Server-authoritative modular monolith

Это означает:

* вся значимая игровая логика выполняется на сервере;
* клиент отправляет только команды;
* клиент не определяет урон, награды, состояние персонажа или результат боя;
* постоянное состояние хранится в PostgreSQL;
* игровые операции выполняются транзакционно;
* backend остаётся одним приложением, разделённым на независимые игровые модули;
* микросервисы, Kafka и Kubernetes на начальном этапе не используются.

Пример правильной команды клиента:

```json
{
  "action": "basic_attack",
  "target_id": "monster-id"
}
```

Клиент не должен отправлять вычисленный урон или новое количество здоровья.

## 5. Почему используется FastAPI

FastAPI выбран, потому что разработчик хорошо знаком с ним.

Отсутствие встроенной административной панели Django не считается критичной проблемой. Для обычного CRUD планируется использовать SQLAdmin.

Через административную панель должны редактироваться:

* персонажи;
* локации;
* переходы;
* шаблоны монстров;
* экземпляры монстров;
* шаблоны предметов;
* таблицы добычи;
* игровые валюты;
* базовые игровые параметры.

Для сложных административных действий позднее могут появиться отдельные интерфейсы:

* просмотр истории валюты;
* просмотр и воспроизведение боёв;
* симуляция баланса;
* выдача компенсаций;
* редактор локаций;
* редактор заданий;
* управление игровыми событиями.

## 6. Производительность Python

Скорость Python не считается проблемой для выбранного типа игры.

Игра пошаговая и событийная. Сервер не выполняет физику или обновление мира 30–60 раз в секунду.

Типичная обработка хода:

1. получить состояние боя;
2. проверить право игрока выполнить действие;
3. рассчитать атаку и эффекты;
4. записать изменения в PostgreSQL;
5. завершить транзакцию;
6. отправить WebSocket-событие.

Расчёт игровых формул значительно дешевле сетевых запросов и операций с базой данных.

Вероятные узкие места:

* неоптимальные SQL-запросы;
* блокировки;
* слишком длинные транзакции;
* конкурентные действия игроков;
* WebSocket-рассылка;
* игровые таймеры;
* повторное выполнение команд;
* экономические дюпы.

`async` используется для эффективного ожидания PostgreSQL, Redis, WebSocket, HTTP и MinIO. Он не предназначен для ускорения CPU-bound расчётов.

Тяжёлые массовые симуляции баланса должны запускаться отдельно от основного API:

* Taskiq worker;
* отдельный процесс;
* `ProcessPoolExecutor`;
* отдельный сервис, если такая необходимость появится.

## 8. Боевая система

### Основные правила

На первом этапе:

* бой один на один;
* игрок управляет одним персонажем;
* противник — один монстр;
* PvP отсутствует;
* пространственной сетки, рядов и позиций нет;
* ход ограничен таймером;
* порядок ходов определяется отдельной характеристикой, условно называемой инициативой;
* бой продолжается после закрытия браузера;
* игрок, закрывший браузер, просто не выполняет действия;
* при истечении таймера сервер выполняет пропуск хода или защитное действие;
* монстр делает ходы автоматически;
* поддерживаются длительные эффекты.

Примеры эффектов:

* яд;
* кровотечение;
* оглушение;
* усиление;
* ослабление;
* защита;
* регенерация.

### Будущее развитие

Позднее должны появиться:

* несколько игроков против одного монстра;
* несколько монстров;
* групповые бои;
* действия вне своего хода;
* лечение союзника;
* защитные реакции;
* PvP;
* группа против группы.

Хотя MVP использует бой один на один, модель данных не должна быть жёстко ограничена двумя участниками.

### Предлагаемые сущности

```text
Battle
BattleParticipant
BattleAction
BattleEffect
BattleLogEntry
```

`BattleParticipant` должен поддерживать как персонажей, так и монстров.

Пример возможных состояний боя:

```text
CREATED
WAITING_FOR_ACTION
RESOLVING_TURN
FINISHED
CANCELLED
```

### Чистый боевой движок

Расчёт боя должен быть отделён от FastAPI и SQLAlchemy.

Пример интерфейса:

```python
def resolve_action(
    battle: BattleState,
    command: BattleCommand,
    rng: Random,
) -> BattleResult:
    ...
```

Боевой движок:

* не выполняет запросы в базу;
* не зависит от FastAPI;
* получает готовое состояние;
* возвращает новое состояние и игровые события;
* поддерживает детерминированные тесты;
* допускает симуляцию тысяч боёв;
* позволяет воспроизводить бой через сохранённый random seed.

## 9. Игровые таймеры

Таймеры используются для:

* длительности хода;
* перемещения;
* возрождения монстров;
* воскрешения персонажа;
* восстановления ресурсов;
* длительности эффектов;
* игровых событий.

Нельзя использовать `asyncio.sleep()` для каждого боя или перемещения.

Нельзя считать `FastAPI BackgroundTasks` надёжным механизмом критичных игровых таймеров.

Источник истины — PostgreSQL.

Примеры временных полей:

```text
battle.turn_deadline_at
travel.arrive_at
monster_spawn.respawn_at
character.resurrection_available_at
```

Рекомендуется универсальная таблица:

```text
scheduled_game_events
────────────────────────────
id
event_type
aggregate_type
aggregate_id
execute_at
status
attempts
deduplication_key
payload
created_at
processed_at
```

Scheduler должен выбирать наступившие события с использованием:

```sql
SELECT *
FROM scheduled_game_events
WHERE status = 'pending'
  AND execute_at <= now()
ORDER BY execute_at
FOR UPDATE SKIP LOCKED
LIMIT 100;
```

Обработчики событий обязаны быть идемпотентными.

## 10. Мир и перемещение

Мир представляется графом локаций.

Основные сущности:

```text
Location
LocationConnection
Travel
```

Переход между локациями занимает реальное время.

Время перемещения позднее может сокращаться через:

* характеристики;
* экипировку;
* ездовых животных;
* расходники;
* дороги;
* порталы;
* премиальные бонусы.

Переход может содержать ограничения:

* минимальный уровень;
* требуемый предмет;
* стоимость;
* выполненное задание;
* активное событие;
* принадлежность к фракции.

Во время перемещения персонаж должен иметь состояние, не позволяющее начать несовместимые действия.

## 11. Игроки в локации и присутствие

Игроки должны видеть других персонажей в локации в виде списка.

Постоянное местоположение персонажа хранится в PostgreSQL:

```text
character.location_id
```

Текущий online-статус хранится временно в Redis через heartbeat и TTL.

Закрытие браузера:

* не перемещает персонажа;
* не завершает бой;
* не удаляет персонажа из постоянного мира;
* только меняет online-статус после истечения TTL.

## 12. Монстры и охота

Монстры в мире общие для всех игроков.

Необходимо разделять шаблон монстра и конкретный экземпляр:

```text
MonsterTemplate
MonsterSpawn
```

Шаблон содержит:

* название;
* уровень;
* базовые характеристики;
* способности;
* таблицу добычи.

Экземпляр содержит:

* текущую локацию;
* текущее здоровье;
* статус;
* активный бой;
* время возрождения;
* максимальное число нападающих.

Возможные статусы:

```text
available
in_battle
dead
respawning
```

При нападении строка экземпляра монстра должна блокироваться транзакционно, чтобы два игрока не создали два независимых боя с одним монстром.

В MVP:

```text
max_attackers = 1
```

Позднее значение может быть увеличено для групповых боёв.

## 13. Персонаж и развитие

Персонаж имеет:

* уровень;
* опыт;
* здоровье;
* силу;
* защиту;
* инициативу;
* экипировку;
* инвентарь;
* игровые валюты.

Классовая система окончательно не определена.

На начальном этапе развитие свободное и основано на:

* характеристиках;
* навыках;
* экипировке.

Архитектура не должна жёстко привязывать персонажа к одному классу, пока правила классов не определены.

## 14. Инвентарь и предметы

Ресурсы и расходники могут складываться в стопки.

Экипировка с прочностью должна храниться отдельными экземплярами.

Это две разные модели хранения.

### Стопки

```text
InventoryStack
────────────────────────────
character_id
item_template_id
quantity
```

### Экземпляры

```text
ItemInstance
────────────────────────────
id
item_template_id
owner_character_id
durability
max_durability
quality
properties
equipped_slot
```

Шаблон предмета:

```text
ItemTemplate
────────────────────────────
id
name
item_type
stackable
max_stack_size
base_durability
base_properties
rarity
```

Два одинаковых меча с разной прочностью считаются разными экземплярами.

## 15. Смерть персонажа

При поражении персонаж становится призраком и попадает в отдельную локацию.

Рекомендуется разделять:

```text
life_state:
    alive
    ghost

activity_state:
    idle
    traveling
    in_battle
```

Не следует создавать один общий enum, смешивающий состояние жизни и текущую активность.

После поражения:

1. бой завершается;
2. персонаж получает `life_state = ghost`;
3. персонаж перемещается в специальную локацию;
4. обычные действия становятся недоступны;
5. персонаж может воскреснуть;
6. после воскрешения он возвращается в определённую локацию.

## 16. Валюты и экономика

В игре планируется несколько валют.

Часть внутренней валюты позднее может покупаться за реальные деньги.

Не следует добавлять отдельное поле в таблицу персонажа для каждой валюты.

Используется универсальная модель:

```text
Currency
WalletBalance
CurrencyTransaction
```

Каждое изменение баланса должно создавать запись в журнале.

Примеры операций:

* награда за бой;
* покупка предмета;
* ремонт;
* торговля;
* административная компенсация;
* покупка премиальной валюты;
* возврат платежа.

Изменение баланса без истории операции недопустимо.

Для MVP достаточно одной обычной валюты. Реальные платежи в MVP не входят.

## 17. WebSocket

WebSocket используется для оперативной доставки событий:

```text
battle.started
battle.turn_started
battle.action_resolved
battle.effect_applied
battle.finished
travel.completed
monster.spawned
location.player_joined
location.player_left
character.updated
```

WebSocket не является источником истины.

После переподключения frontend должен запросить актуальное состояние через HTTP API.

Пример:

```http
GET /api/v1/battles/current
```

При нескольких FastAPI workers события должны передаваться между процессами через Redis.

Нельзя полагаться на список подключений, хранящийся только в памяти одного процесса.

## 18. Идемпотентность и конкурентный доступ

Каждая изменяющая игровая команда должна иметь `idempotency_key`.

Это необходимо для защиты от:

* двойного клика;
* повторной отправки запроса;
* сетевого retry;
* повторного выполнения фоновой задачи.

Критичные действия выполняются внутри коротких транзакций.

Для защиты состояния используются:

* `SELECT ... FOR UPDATE`;
* optimistic locking через поле `version`;
* уникальные ограничения;
* idempotency key;
* проверка текущего состояния сущности.

Особенно важны конкурентные операции:

* атака монстра;
* выполнение хода;
* получение награды;
* покупка;
* использование предмета;
* ремонт;
* торговля;
* изменение валютного баланса.

## 19. Использование Taskiq

Taskiq используется для задач, не являющихся непосредственной частью критичного игрового состояния:

* AI-генерация изображений;
* генерация описаний;
* создание текстов заданий;
* обработка файлов;
* отправка писем;
* экспорт данных;
* сбор статистики;
* пересчёт рейтингов;
* очистка данных;
* тяжёлые симуляции.

Критичные таймеры боёв, перемещений и возрождения должны оставаться в PostgreSQL и обрабатываться отдельным scheduler.

* PvP;
* групповые бои;
* торговля между игроками;
* аукцион;
* реальные платежи;
* кланы;
* профессии;

## 23. Правила для AI-агентов

При работе с проектом агенты должны придерживаться следующих принципов:

1. Не предлагать переход на микросервисы без фактической необходимости.
2. Не хранить критичное игровое состояние только в памяти или Redis.
3. Не использовать `asyncio.sleep()` как основной механизм игровых таймеров.
4. Не помещать бизнес-логику в FastAPI routers.
5. Не выполнять SQL-запросы внутри чистого боевого движка.
6. Не доверять значениям урона, наград или состояния, присланным клиентом.
7. Любые изменения валюты должны оставлять запись в журнале.
8. Экипировка с прочностью должна храниться отдельными экземплярами.
9. Расходники и ресурсы должны храниться стопками.
10. Любая критичная команда должна быть идемпотентной.
11. WebSocket используется только для доставки событий, а не как источник истины.
12. Любая оптимизация должна основываться на измерениях и нагрузочных тестах.
13. При проектировании MVP не добавлять механики из списка «не входит в MVP», если они не нужны для текущего вертикального среза.
14. Новая функциональность должна сохранять возможность тестировать игровую логику без FastAPI и PostgreSQL.
15. Предпочитать простые и понятные решения, подходящие одному разработчику.
